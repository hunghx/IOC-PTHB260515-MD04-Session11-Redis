1. Giới Thiệu Redis & Kiến Trúc In-Memory Data Store
📌 Bản Chất Của Redis

Redis (REmote DIctionary Server) là hệ quản trị cơ sở dữ liệu NoSQL lưu trữ trực tiếp trên bộ nhớ RAM (In-Memory Key-Value Data Store), cung cấp tốc độ đọc ghi tính bằng micro-giây.

🚀 4 Use Case Kinh Điển Trong Microservices
1. Database CachingLưu bản sao kết quả truy vấn để giảm tải cho DB chính
2. Distributed SessionQuản lý phiên đăng nhập dùng chung cho nhiều instances
3. Fast Pub/SubTruyền tin nhắn thời gian thực (Chat, Notification tức thì)
4. Distributed LockKhóa phân tán ngăn tranh chấp tài nguyên (trừ tồn kho, flash sale)

2. Cơ Chế Hết Hạn Dữ Liệu (TTL & Eviction)
# Đặt key kèm thời gian sống (TTL = 60 giây)
SET user:token:123 "valid" EX 60

# Kiểm tra thời gian còn lại (giây)
TTL user:token:123

• TTL (Time-To-Live): Tự động dọn dẹp bộ nhớ khi dữ liệu hết hạn.
• MaxMemory Policy: Khi RAM đầy, Redis áp dụng chính sách allkeys-lru (loại bỏ key ít truy cập nhất gần đây) để nhường chỗ cho dữ liệu mới.

3. Cơ Chế Cache-Aside (Look-Aside) & Cache Hit / Miss
Mô Hình Cache-Aside Hoạt Động Ra Sao?
  1. Ứng dụng kiểm tra dữ liệu trong Redis với key tương ứng.
  2. Nếu có (Cache Hit): Trả về ngay lập tức, bỏ qua Database.
  3. Nếu chưa có (Cache Miss): Đọc từ Database chính ➔ Lưu kết quả vào Redis kèm TTL ➔ Trả về cho Client.
Chiến Lược Cập Nhật Cache Khi Dữ Liệu Thay Đổi
Write-ThroughGhi đồng thời vào cả Cache và Database
Cache InvalidationKhi DB cập nhật/xóa ➔ Xóa key tương ứng trong Redis (Khuyên dùng)

4. Cài Đặt Spring Cache Với Redis Annotations
1. Dependency & Cấu hình application.yml

    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>

# application.yml

    type: redis
  data:
    redis:
      host: localhost

2. Sử Dụng Các Annotation Tiêu Chuẩn
@Service
public class ProductService {

    // Tìm thấy trong cache thì trả về ngay, chưa có mới chạy hàm
    @Cacheable(value = "products", key = "#id")
    public Product getProductById(Long id) {
        return productRepo.findById(id).orElseThrow();
    }

    // Khi update sản phẩm thì xóa cache cũ để tránh dữ liệu rác
    @CacheEvict(value = "products", key = "#product.id")
    public Product updateProduct(Product product) {
        return productRepo.save(product);
    }
}

5. Cơ Chế Giao Tiếp Thời Gian Thực Với Redis Pub/Sub
Đặc Tính Cốt Lõi Của Redis Pub/Sub

• Cơ chế Fire-and-Forget: Publisher gửi tin lên Channel, Redis phát ngay lập tức tới tất cả Subscriber đang online.
• Không Lưu Trữ (No Persistence): Nếu Subscriber đang offline lúc gửi, tin nhắn đó sẽ bị mất vĩnh viễn và không nhận lại được.
• Tốc độ cực nhanh: Độ trễ cực thấp tính bằng phần nghìn giây.

Khi Nào Nên Dùng Redis Pub/Sub?
Phù hợpChat trực tiếp, thông báo tức thời WebSockets, thông báo refresh cache hệ thống
Không phù hợpGiao dịch tài chính, thanh toán, đặt đơn hàng (vì không đảm bảo lưu trữ nếu lỗi)

6. Cài Đặt Redis Pub/Sub Với RedisTemplate & MessageListener
1. Code Publisher (Phát Tin Nhắn)
@Service
public class NotificationPublisher {

    @Autowired
    private StringRedisTemplate redisTemplate;

    public void publishMessage(String channel, String msg) {
        // Gửi message vào channel chỉ định
        redisTemplate.convertAndSend(channel, msg);
        System.out.println("Đã phát tin lên: " + channel);
    }
}
2. Code Subscriber (Lắng Nghe Tin Nhắn)
@Component
public class RedisMessageSubscriber implements MessageListener {

    @Override
    public void onMessage(Message message, byte[] pattern) {
        String body = new String(message.getBody());
        String channel = new String(message.getChannel());
        System.out.println("Nhận từ [" + channel + "]: " + body);
    }
}
NÂNG CAO Lesson 4 • Redis cho distributed lock
7. Bài Toán Khóa Phân Tán (Distributed Lock) Trong Microservices
Vì Sao synchronized Java Bị Vô Hiệu Hóa?

Khóa của Java (synchronized, ReentrantLock) chỉ có tác dụng trong cùng 1 máy ảo JVM. Khi hệ thống mở rộng chạy nhiều container Docker độc lập, hai user truy cập đồng thời vào hai container khác nhau sẽ gây ra hiện tượng Race Condition (Bán âm kho, trừ tiền 2 lần).

Nguyên Lý Của Redis Distributed Lock

Lợi dụng tính chất Single-Threaded của Redis với lệnh nguyên tử (Atomic):
SET lock_key unique_value NX PX 30000
• NX: Chỉ tạo nếu key CHƯA tồn tại (Lấy khóa thành công).
• PX 30000: Hết hạn sau 30 giây để chống Deadlock nếu service bị chết.

8. Triển Khai Distributed Lock Chuẩn Production Với Redisson
1. Code Sử Dụng Redisson Lock
@Service
public class OrderService {

    @Autowired
    private RedissonClient redisson;

    public void buyProduct(Long productId) {
        RLock lock = redisson.getLock("lock:product:" + productId);
        try {
            // Chờ tối đa 5s để lấy khóa, tự nhả sau 10s
            if (lock.tryLock(5, 10, TimeUnit.SECONDS)) {
                // Độc quyền trừ tồn kho an toàn
                inventoryService.deductStock(productId);
            }
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock(); // Luôn nhả khóa trong finally
            }
        }
    }
}

9. Bảng So Sánh Toàn Diện: RabbitMQ vs Apache Kafka vs Redis
Tiêu chí so sánh 🐰 RabbitMQ 🚀 Apache Kafka ⚡ Redis (Pub/Sub & Streams)
Bản chất cốt lõi Traditional Message Broker (AMQP) Distributed Streaming Commit-Log In-Memory Cache & Lightweight Pub/Sub
Cơ chế lưu trữ Lưu tạm, xóa ngay sau khi Consumer Ack Lưu vĩnh viễn / lâu dài trên ổ đĩa theo thời gian Lưu trên RAM (Pub/Sub không lưu; Streams lưu có giới hạn)
Khả năng đọc lại (Replay) ❌ Không thể đọc lại tin đã xóa ✅ Đọc lại thoải mái bằng cách chỉnh Offset ❌ Pub/Sub không hỗ trợ (Streams có hỗ trợ đọc lại)
Định tuyến tin nhắn (Routing) Rất linh hoạt (Direct, Topic, Fanout, Headers) Đơn giản (Dựa theo Topic và Partition Key) Cơ bản theo Channel Pattern (vd: order.*)
Thông lượng (Throughput) Khá (20k - 50k msgs/giây) Cực khủng (Hàng triệu msgs/giây) Rất cao (100k+ msgs/giây trên RAM)
Mô Hình Xử Lý Message

• RabbitMQ (Smart Broker, Dumb Consumer): Broker tự theo dõi trạng thái từng tin nhắn, điều phối gửi cho ai.
• Kafka (Dumb Broker, Smart Consumer): Broker chỉ lưu log, Consumer tự lưu giữ vị trí Offset mình đang đọc tới đâu.

Độ Trễ Phản Hồi (Latency)

• Redis: Nhanh nhất (< 1 ms) do hoàn toàn trên RAM.
• RabbitMQ: Vài mili-giây.
• Kafka: Tối ưu cho thông lượng theo lô (Batching), độ trễ 2 - 10 ms.

10. Cẩm Nang Lựa Chọn Công Cụ Cho Dự Án Thực Tế
🐰 Khi nào chọn RabbitMQ?
  • Cần giao tiếp dạng Task Queue phức tạp (Background Job, xử lý ảnh, xuất file PDF).
  • Cần định tuyến tin nhắn nâng cao (Routing Rules phức tạp cho từng phòng ban).
  • Xử lý theo kiểu Transaction: Tin nào xong tin đó, có Retry/Dead Letter linh hoạt từng message.
🚀 Khi nào chọn Kafka?
  • Kiến trúc Event-Driven Microservices quy mô lớn (Đơn hàng, Thanh toán, Tồn kho).
  • Cần đọc lại dữ liệu lịch sử (Replay events) khi có service mới khởi tạo.
  • Thu thập log tập trung, phân tích dữ liệu lớn thời gian thực (Big Data / Stream Processing).
⚡ Khi nào chọn Redis?
  • Cần tốc độ siêu nhanh & độ trễ cực thấp mà chấp nhận được mất dữ liệu nếu sự cố.
  • Tính năng thời gian thực đơn giản: Thông báo đẩy, WebSocket broadcast, đồng bộ Cache.
  • Hệ thống quy mô vừa và nhỏ, muốn tận dụng Redis có sẵn để làm queue/pubsub mà không cần cài thêm Kafka.
💡 Mô Hình Kết Hợp Chuẩn Trong Doanh Nghiệp Lớn

Trong thực tế, các doanh nghiệp không chọn loại trừ lẫn nhau mà phối hợp cả 3 công nghệ:
• Dùng Redis để Cache dữ liệu và Khóa phân tán (Distributed Lock) khi trừ kho.
• Dùng Kafka làm xương sống truyền sự kiện nghiệp vụ lõi (Event Bus) giữa các Microservices.
• Dùng RabbitMQ để quản lý hàng đợi xuất báo cáo, gửi email và tác vụ ngầm.
